# Ядро — task-agnostic, устойчивый к memory-injection защищённый агент

> 🇬🇧 English version: [kernel.md](kernel.md)

Ядро — это **переиспользуемая основа** проекта и его главный исследовательский вклад:
рантайм защищённого агента, чьи гарантии безопасности держатся **независимо от того,
что языковой модели велено делать** — в том числе вредоносным содержимым, подброшенным
в её собственную память. Оно ничего не знает про аудит смарт-контрактов (или любую
другую задачу). Аудит-агент — это лишь [первый capability-пак](https://github.com/RamilRamil/araratsec-agent),
который на нём едет.

## Суть

Большинство агентных фреймворков держат все возможности и все guardrail'ы в одном
месте, где хитро сформулированный промпт (или отравленная запись памяти) может
уговорить модель обойти guardrail. Ядро вместо этого разбивает систему на две
плоскости:

```
┌──────────── Плоскость оркестрации (детерминированный код) ─────────────────────┐
│  DATA-обёртка · иерархия доверия SourceType · HMAC append-only память ·        │
│  out-of-band gate подтверждения · бюджет tool-call'ов на ход · эскалация ·     │
│  path-containment + сетево-изолированный sandbox                                │
└──────────────────────────────────────┬────────────────────────────────────────┘
                                        │ узкий типизированный интерфейс
┌──────────────────────────────────────▼────────────────────────────────────────┐
│  Плоскость LLM-контекста (вероятностная модель)                                 │
│  локальная модель / relay / платный API · каждый внешний артефакт [DATA]…[DATA] │
└─────────────────────────────────────────────────────────────────────────────────┘
```

Вся безопасность живёт в плоскости оркестрации, в обычном коде. Модель может только
*предлагать*; решает — ядро. Атака prompt-injection или memory-injection способна
изменить то, что модель предлагает, но не то, что ядро разрешает. Полная карта модулей —
в [diagrams/kernel-architecture.ru.md](diagrams/kernel-architecture.ru.md).

Целевая угроза — **Memory Injection (MI)**: вредоносное содержимое, подброшенное в
память агента, которое направляет будущие сессии на эксфильтрацию, пропуск анализа или
ложный вердикт «безопасно». Незащищённые агенты показывают 55–85% успеха атаки;
архитектурные контроли ядра гонят это к ≤5% — по построению, а не по формулировке
промпта.

## Инварианты ядра (гарантии, которые пак не может ослабить)

1. **DATA-обёртка** — каждый вывод инструмента и каждый артефакт прошлого хода,
   возвращающийся в модель, оборачивается в `[DATA START]…[DATA END]` и трактуется как
   данные, никогда как инструкция (`orchestrator/context.py`).
2. **Иерархия доверия SourceType** — каждая запись памяти несёт тир происхождения, и
   порядок доверия — это константа ядра, а не рантайм-состояние
   (`models/memory.py`, `TRUST_LEVELS`):

   | тир | значение | кто/что |
   |------|-------|----------|
   | `human_input` | 4 | оператор, in-band |
   | `tool_output` | 3 | инструмент из whitelist |
   | `external_llm_output` / `human_relayed_tool` | 2 | вывод модели / релеенный текст инструмента |
   | `llm_inference` | 1 | собственные рассуждения модели |

   Вывод модели/relay **никогда** не повышается до `human_input`.
3. **HMAC append-only память** — каждая запись HMAC-подписана оркестратором
   (`memory/hmac.py`, `memory/episodic.py`); записи, не прошедшие проверку, молча
   отбрасываются до попадания в модель. Никаких update/delete — исправления это новые
   записи, которые `supersede`, и только `human_input` может их выпускать или ставить
   привилегированные статусы. Подписан не только каждый запись, но и весь набор:
   цепочка записей и подписанный `_chain_head.json` делают удаление и обрезку хвоста
   детектируемыми (фича 004); откат всего каталога к более старой валидной копии
   ловится per-project HMAC-watermark'ом **вне** `memory_root` (`SR_ANCHOR_ROOT`, фича
   006) — `snapshot`/`write` fail-closed, когда лог короче точки, которую он заведомо
   уже проходил. Гарантия настолько сильна, насколько оператор разделил доступ к
   `anchor_root` и `memory_root`; без переменной guard инертен.
4. **Out-of-band gate подтверждения** — необратимое/привилегированное действие ставит
   run на паузу и требует осознанного одобрения через *отдельный* канал. Это
   **выводится ядром** из `action.action_class == write_execute`
   (`orchestrator/action.py::validate_action`), а не из флага, выставленного паком.
5. **Бюджет tool-call'ов на ход** — жёсткий лимит вызовов инструментов за ход.
6. **Механика эскалации** — путь рассуждения может эскалировать (local → relay/сильнее)
   при низкой уверенности или самозаявленной неопределённости; тир всегда виден
   (`guardrails/escalation.py`, `orchestrator/relay.py`).

Всё это обеспечивается кодом и покрыто тестами (включая property-тест на враждебный пак:
пак, пытающийся зарегистрировать `write_execute`-инструмент как не требующий
подтверждения или сочинить контент тира `human_input`, отклоняется/бессилен —
`tests/security/test_hostile_pack.py`, `tests/architecture/test_kernel_pack_boundary.py`).

## Модули ядра

```
sr_agent/
  orchestrator/   loop (OrchestratorLoop.run / run_turn), action (validate_action),
                  confirmation (OOB gate), context (DATA-обёртка), chat_session,
                  pack (интерфейс CapabilityPack), relay (ручной/файловый reasoning)
  guardrails/     sanitize, escalation (обобщённые триггеры)
  memory/         episodic (HMAC-хранилище), hmac, knowledge, lessons
  models/         memory (SourceType/MemoryRecord), action, principal, session, chat
  llm_core/       local_client, claude_client, gemini_client, openrouter_client,
                  router (резолвит routing[role]), chat_reasoning, schemas
  tools/          registry (механизм whitelist), sandbox (--network none Docker),
                  readonly
  config.py       конфиг из env      io/progress   eval/tracer (Langfuse)
```

Правило границы (проверяется архитектурным тестом): **ни один модуль ядра не импортирует
ни один downstream-модуль пака.** Паки зависят от ядра, никогда наоборот.

> **Замечание — здесь не поставляется composition root.** Ядро — только для импорта
> (`sr_agent`, без `[project.scripts]`, без `cli.py`). Его запускает composition root,
> живущий **downstream** — в репозитории [araratsec-agent](https://github.com/RamilRamil/araratsec-agent):
> CLI `sr-agent` (`audit_agent/cli.py`) и operator-фронтенд (`frontend/backend/app.py`).
> Оба собирают один и тот же `OrchestratorLoop(pack=…, …)`.

## Интерфейс CapabilityPack

Пак **декларативен и ограничен**. Подключается через один frozen-dataclass
(`sr_agent/orchestrator/pack.py`):

```python
CapabilityPack(
    name,                 # str
    actions,              # Mapping[str, ActionSpec]  — action_class, is_reversible, validate_params
    tools,                # Sequence[ToolDefinition]  — name, description, handler
    privileged_statuses,  # frozenset[str]            — доменные статусы, доступные только human_input
    reasoning_prompt,     # str
    dispatch / execute_confirmed / persist_finding,   # доменные callable'ы
    domain_escalation, signal_from,                   # доменные callable'ы
)
```

Callable'ы пака получают только узкий `PackContext` — **никогда loop, никогда handle на
запись памяти**. Пак может регистрировать инструменты и помечать действия
высокорисковыми, но у него нет рычага пропустить OOB-gate, подделать тир доверия или
тронуть HMAC-хранилище. Динамического реестра плагинов намеренно **нет** — единственный
пак подключён явно (YAGNI); ценность — сама граница.

## Охват — task-agnostic на уровне гарантий *и* идентификаторов

**Гарантии** ядра task-agnostic и MI-доказаны против внутрирепозиторного
[fixture-пака](../tests/fixtures/pack/), где нет никакого аудит-кода. Фича 001
(task-agnostic контракт действий) устранила остаточное именование, оставшееся от
до-раскольного монорепо:

- **Таксономия действий ОТКРЫТА.** `Action.action_type` — свободная `str`, а не
  закрытый доменный enum. Доменные id анализаторов (`run_slither`, `write_poc`, …)
  живут в `actions` пака; ядро держит только обобщённые, недоменные id, которые оно
  предоставляет каждому паку — control/memory-машинерию (`write_memory`,
  `request_human_confirmation`) и scope-ограниченные чтения (`read_file`,
  `search_code`, решение D6). `validate_action` резолвит id против
  `KERNEL_GENERIC_ACTIONS ∪ pack.actions`, fail-closed при промахе. `write_memory`
  исполняется ядром — `KernelActionExecutor.execute` перехватывает его до
  `pack.dispatch`; пак никогда не вызывается и не должен его стабить (фича 002,
  см. ниже).
- **Привилегированные статусы объявляет пак.** Ядро не хардкодит ни одного; каждый
  пак объявляет свои, а ядро биндит этот набор в `EpisodicMemory` при
  конструировании сессии (решение D5). Пустой = «этот пак ничего не гейтит», а не
  «гейт выключен».
- **`PackContext` доменно-нейтрален:** `scope_root`, `sandbox`, `wrap_data`.
  PoC-состояние (`poc_dir`/`poc_generator`) ушло из контекста (решение D2) — пак,
  запускающий write_execute PoC-путь, несёт своё. Переходный `__getattr__`-шим
  отвечает на `ctx.audit_root` → `scope_root` с `DeprecationWarning`, пока аудит-пак
  не мигрирует (снимается в PR-3).
- `orchestrator/loop.py` возвращает доменно-нейтральный `RunResult`; валидаторы
  чтений принимают `scope_root`.

Это закреплено тестом границы **B6** (`tests/architecture/test_kernel_pack_boundary.py`):
открытый `action_type`, отсутствие доменного id и привилегированного статуса как
операционных в `sr_agent/`, и точные наборы kernel-generic / loop-terminal.

**Остаточный residue (отдельная задача):** *модель finding* всё ещё несёт
аудит-словарь — `FindingPayload.bastet_tag` в `llm_core/schemas.py` и relay
`_RESPONSE_SCHEMA`. Деменизация finding-схемы — вне охвата фичи 001 (таксономия
действий + статусы) и ведётся как отдельный follow-up.

## Что нужно для запуска

Ядро не запускается само по себе — его ведёт **composition root**, спаривающий его с
паком. Требования:

- **Python ≥ 3.11**, зависимости из `pyproject.toml`.
- **`SR_SECRET_KEY`** (32-байтный hex) — ключ HMAC-подписи. Обязателен. Остальные корни
  (`SR_MEMORY_ROOT`, `SR_CONFIRMATIONS_ROOT`, `SR_RELAY_ROOT`) по умолчанию `./…`.
- **Reasoning-бэкенд** — локальная модель через Ollama (`local_client`), ручной файловый
  **relay** (`orchestrator/relay.py`) или (по желанию) хостед-API
  (`claude_client` / `gemini_client` / `openrouter_client`). Платный ключ для запуска не
  нужен; reasoning-бэкенд — рантайм-выбор, а не build-time.
- **Docker** — только если пак исполняет код под влиянием атакующего/модели, который ядро
  всегда гоняет `--network none` в эфемерном sandbox (`tools/sandbox.py`).

Пак, демонстрирующий всё это, — в downstream-репозитории
[araratsec-agent](https://github.com/RamilRamil/araratsec-agent), а историю изменений
этого бандла см. в [log.md](log.md).

## Dispatch, resume и лимит снимка (feature 003)

Фича `003-dispatch-result-resume` проводит chat и batch через один
`KernelActionExecutor`. Pending пишет ровно один `pause_checkpoint` и снимает
writer lease; resume собирает Action из снимка и не просит модель повторить его.
Байты system prompt берутся из доверенного `PromptRegistry`. В чекпоинте только
`system_prompt_id` / `system_prompt_hash` как ссылка.

`MemorySnapshot` — единственный read seam пака. Лимит: **10000 записей / 32 MiB**.
Превышение — fail closed. Оператор **завершает сессию и начинает новую**, а не
обрезает снимок (FR-009b).

## `write_memory` и наблюдаемость памяти (feature 002)

`write_memory` — это машинерия ядра, а не возможность пака:
`KernelActionExecutor` распознаёт этот id действия ещё до `derive_ids`/
`pack.dispatch` и обрабатывает его сам, из фиксированной формы записи — никогда
через `pack.dispatch` и никогда напрямую из `action.params`. Пак ничего для
него не объявляет, и его никогда не просят его застабить.

- **Provenance задаёт ядро.** Записанная запись всегда несёт
  `source_type=llm_inference`. Параметры модели могут задать только текст
  заметки (и опциональный ограниченный `target`); любая попытка задать
  `source_type`, `hmac`, `supersedes`, `status_change` или другое поле
  идентичности **отклоняется** на этапе валидации, а не тихо вырезается.
- **Контент — обычная заметка**, а не finding: `payload={"note": …}`,
  `payload_kind="model_note"`. Репортинг finding остаётся на существующем пути
  `persist_finding` — модель не вызывает `write_memory`, чтобы сообщить о
  finding.
- **Не переход.** У `write_memory` нет `operation_id`, нет `commit_if_absent`,
  и он не двигает `session_revision`; две одинаковые заметки — это две разные
  записи, а не одна дедуплицированная.
- **Исключён из `SNAPSHOT_KINDS`.** `model_note` относится к tier
  `llm_inference` и намеренно никогда не попадает в `MemorySnapshot` —
  собственная заметка модели не может стать посылкой для проекции пака.
- **Никакого нового OOB-гейта.** `ActionClass.memory` по-прежнему не получает
  out-of-band подтверждения; этот гейт остаётся только `write_execute` плюс
  привилегированные статусы, объявленные паком.

Отдельно — каждая успешная запись `EpisodicMemory.write` (заметка модели,
finding, реплика чата, снимок сессии, что угодно durable) теперь порождает
полноценное live-trace событие `memory_write`, отличное от событий
`tool`/`reasoning`/`routing`. Событие несёт только метаданные (никогда тело
записи, никогда `hmac`/`seq`/`chain_prev`). Sink биндится один раз при
конструировании `EpisodicMemory`; отсутствующий или падающий sink никогда не
блокирует и не откатывает запись, о которой он должен был сообщить.

## Provenance для finding (feature 005)

До этой фичи `OrchestratorLoop` сохранял finding, о котором сообщила модель,
в момент самого сообщения — и в `run`, и в `run_turn` — до терминальной
проверки, до `validate_action` и до `executor.execute`. Подписанный `Finding`
существовал независимо от того, пошёл ли ход дальше запускать инструмент,
предложил ли действие, которое ядро отклонило, назвал ли действие, которого
никто не знает, или просто завершился. Ничто в записи не различало эти
случаи. Это никогда не было пробоем trust-tier — запись имеет
`source_type=external_llm_output` и никогда не повышается — но это был
пробел в доказательствах: хранилище отвечало на вопрос "сказала ли это
модель" и молча читалось как ответ на вопрос "было ли это на чём-то основано".

Исправление помечает каждую запись finding тем, что ядро реально
пронаблюдало о действии, предложенном в ТОМ ЖЕ `AgentAction`, как только это
действие разрешилось:

| Поле | Значения |
|---|---|
| `action_resolution` | `"resolved"` \| `"unresolved"` \| `"pending"` \| отсутствует |
| `action_operation_id` | `str` \| отсутствует |
| `action_dispatch_status` | значение `DispatchStatus` \| отсутствует |
| `resolves_record_id` | `str` \| отсутствует |

| Случай | `action_resolution` | `action_operation_id` | `action_dispatch_status` | `resolves_record_id` |
|---|---|---|---|---|
| dispatch разрешился | `resolved` | есть | терминальный | отсутствует |
| отклонено · неизвестный id · терминал без инструмента | `unresolved` | отсутствует | отсутствует | отсутствует |
| пауза | `pending` | есть | `pending` | отсутствует |
| запись разрешения при resume | `resolved` | есть | терминальный | есть |
| записано до kernel/005 | отсутствует | отсутствует | отсутствует | отсутствует |

Другой комбинации не существует: `MemoryRecord._provenance_is_coherent`
отказывает в противоречивом штампе уже при конструировании, потому что
append-only хранилище не может исправить его задним числом.

**Намеренно нет поля `grounded`, ни под этим, ни под каким другим именем, и
не будет.** Ядро наблюдает совпадение во времени в рамках одного хода
модели — исход действия, предложенного вместе с finding, — а не деривацию.
Модель может привязать finding к действию, с которым он никак не связан.
`DispatchStatus.ran` означает, что dispatch завершился, а не что анализатор
произвёл обоснованный результат, и собственный docstring `DispatchStatus`
уже называет схлопывание этих двух вещей ошибкой. Флаг ядра, утверждающий
более сильное, создал бы уровень доказательности, который ничем не
верифицирован — и это было бы хуже, чем закрываемый им пробел: сегодня
потребитель знает, что `Finding` — гипотеза, тогда как флаг обоснованности
приглашает перестать это знать. Обоснованность — это политика потребителя
над фактами ядра, а не факт самого ядра.

**Пара при паузе.** Finding, о котором сообщили в ходе, который приостановился,
не может ждать resume для записи — он должен пережить сбой и оставаться
видимым в снимке, пока человек решает вне канала. Поэтому приостановленный
ход сразу пишет `pending`, а resume пишет ВТОРУЮ запись, `resolved`, с
`resolves_record_id`, называющим первую. Эта вторая запись — не
`supersedes`: `supersedes` отклоняется на всём, кроме
`source_type=human_input` ("исправления существующих записей требуют
человеческого авторитета"), а finding остаётся `external_llm_output` —
выставить человеческий уровень, чтобы пройти эту проверку, было бы именно
тем повышением, которое запрещает Constitution I. Ослабление правила вместо
этого сделало бы ядро вторым авторитетом, способным удалять записи по id,
поскольку `supersedes` убирает замещённую запись из каждой загрузки и из
снимка. Приостановленная запись сохраняет свой `record_id`, который остаётся
стабильным адресом finding — потребитель, захвативший этот id до
подтверждения, после него всё ещё адресует тот же finding.

**Целостность.** Все четыре поля исключены из `fields_for_hmac()`, когда не
заданы, поэтому хранилище, записанное до этой фичи, верифицируется точно
так же, как раньше — безусловное добавление подписываемых полей изменило бы
подписанную форму каждой записи на диске и обнулило бы всё хранилище. Если
поле задано, оно подписывается как любое другое поле: изменение или
вырезание его впоследствии ломает подпись записи. Пути понижения нет —
подписание происходит в момент записи, а не чтения, поэтому запись,
несущую provenance, нельзя заставить читаться как legacy-unknown, убрав из
неё поля.

**`for_llm_context()` вырезает все четыре поля** — по той же причине, по
которой уже вырезается `log_sequence`: ход, способный видеть собственную
бухгалтерию, способен о ней рассуждать, а затем спорить с ней. Поля
provenance — более острый случай: они называют именно то состояние, которое
делает finding пригодным для доказательства ниже по цепочке, так что модель,
видящая, какой из её собственных прошлых finding получил такой штамп, могла
бы оптимизироваться под его получение. Пак читает их из `SnapshotItem` —
это проекция, построенная для пака, а не контекст модели.

**Отсутствие означает неизвестно, никогда не "действие не разрешилось".**
Запись, сделанная до этой фичи, ничего не говорит о своём ходе; читать её
отсутствующие поля как `unresolved` значило бы придумать утверждение, которое
ядро никогда не делало.
